The main search runs on cubiomes, which is fast because it never builds the world. These questions need something it cannot see — real decoration, real structure pieces, a real server — so each has its own engine. Open one to use it. The chat box will also route to these on its own when a question needs them.

Village buildings real worldgen Seeds whose village holds N smiths — by running Minecraft's own generator (MC 1.16.5). Slow.
why this needs its own engine
A village is a jigsaw structure: which buildings it gets is decided while the world generates, so nothing short of the real generator can see inside one. Counts tool/weapon/armorer as "any smith".
Treasure casing real worldgen A buried treasure walled in by magma, copper ore, gravel… Roughly 1 in 6 600 chests for the rare ones.
why this needs its own engine
A buried treasure writes the block it landed on into every air or water face around it — so it arrives already walled in. The main search cannot ask this: it runs on cubiomes, which has no surface rules and no decoration, so sand columns, ore and magma are absent from that engine rather than slow. Measured over 6 646 chests: sand 78%, gravel 18%, dirt 2.7%, stone 0.9% — and copper ore and magma ~0.015% each, about 6 600 chests scanned per expected hit.
Blocks per world decides how much of each world is actually examined. The finder reports only the first treasure in a seed, so this expands it to every treasure within that radius — 6 chests at 1 500, 1 431 at 20 000. For a rare casing that is the difference between searching a world and glancing at it.
Keep looking open-ended Runs the query in the chat box batch after batch on fresh seeds until it finds one, or you stop it.
why this is not just pressing Search again
The normal search walks seeds starting from the same place every time, so running it again re-scanned the same ground. This moves on to fresh seeds each batch.
Fortresses inside each other piece-level Ranks seeds by how many fortress pieces actually intersect — not by how close the starts are.
why "close together" is the wrong measure
A fortress is up to 257 pieces sprawling 112 blocks from its start, and each is generated without knowing the others exist — so two starts 80 blocks apart do not sit near each other, they grow through each other. This counts intersecting piece pairs.
Exposed treasure real worldgen A buried treasure chest sitting in open air — no digging.
why this needs its own engine
The chest is placed at the bottom of the sand column, so it is almost always covered or underwater; this needs a beach with essentially no sand over the stone. cubiomes cannot see it (no sand, no water), so real worldgen decides.
What is cool in my seed? per-seed The opposite of a search: hand it a world you already have and it reads every lootable chest in range.
what it reads
Leave the item blank for anything notable, or name one to hunt it specifically. Enchantments and their levels are read — put an enchantment in the box below to find e.g. a Looting III golden sword.
Cave spiders by a village real pieces Villages with mineshaft spider-spawner corridors next door.
how the spawners are counted
Cave spider spawners come from mineshaft spider corridors, which are structure pieces — so the real generator can enumerate them and the game's own spiderCorridor flag says which ones get a spawner. Corridors the game would skip (a piece touching liquid is dropped outright) are not counted. Distance is in chunks.

These are spawners that exist. Whether you can reach one is a terrain question this does not answer — ordinary mineshafts sit near y −30.
Bedrock glitched outpost Bedrock Edition The outpost on a tall cobblestone pillar. Does not exist in Java. Runs a real Bedrock server — slow.
why Java can never do this
Java drops a small dirt platform under a structure that lands in air, while Bedrock fills a foundation to the ground out of the structure's own material. This runs a real Bedrock Dedicated Server and measures the column block by block, so the height reported is measured rather than predicted. Bedrock seeds do not transfer to Java, so this never falls back to the Java search.
Really overlapping? piece-exact Checks one pair you already found. Exact for fortress and end_city; answers UNKNOWN otherwise.
why the search's own answer is not enough
The search compares nominal boxes, and its distance is measured origin to origin — a mansion sprawls far past its origin, so a pair reported 57 blocks apart had buildings ~15–20 apart. This intersects the structures' real piece bounding boxes. UNKNOWN is not the same as “they don't overlap”.
Actually floating? no server Confirms one spot: is that structure genuinely in the air, or just on a hillside?
why the search's floating flag was wrong
The search's floating condition comes from a density function, and two earlier versions of it called 18–24% of outposts floating — on a hillside the ground genuinely is missing at those heights. This reads the real terrain column out of Minecraft's own generator and wants three things at once: a solid cap, a real void beneath it, and ground that drops away on nearly every side. It answers UNKNOWN rather than guessing when it cannot see.
